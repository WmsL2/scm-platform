# 类型4自由推品 Agent 与 Web

## 1. 使用流程

1. 在投标与推品项目页面选择“类型4 · 自由推品 Agent”。
2. 填写项目、需求方和不少于 20 字的场景需求说明。
3. 上传本项目的推荐结果 `.xlsx` 模板。
4. 创建后确认工作表、表头行、数据起始行和模板字段映射。左侧展示上传模板的真实列名和列序号且不可修改，右侧从商品主数据字段中搜索选择要写入的数据；重复表头按各自列号独立映射，同一商品字段可写入多个模板列。
5. 启动 Agent，查看实际解析的筛选条件和分页候选。
6. Agent 生成全部符合条件的候选后，项目自动进入“待选品”。运营可分页勾选、批量确认或逐条补充活动价、履约说明和依据。
7. 点击“完成选品”后项目进入“选品完成”，导出文件只包含右侧人工选择的商品。
8. 导出后项目自动进入“已生成报价”；使用最新导出文件标记投标后进入“已投标”，再由运营登记“已中标”或“未中标”。

自由推品允许类目、品牌、价格区间、预算和数量留空。数值价格条件始终是硬条件；仅客户以“必须、仅限、指定、只要”等强制语气提出的品牌才会成为硬条件。类目在客户强制指定、直接提出具体商品类型（如“需要水杯、保温杯、随行杯”）或以“家电 250 个、厨具 135 个、日用 115 个”明确给出类目分配时，都会成为硬条件。明确类目会使用其近义类目词匹配商品三级类目，避免名称不同而漏召回；数字本身一律忽略，不限制候选数量。节日、活动、人群、场景、用途、库存和履约物流不参与筛选。

当状态为“需要补充信息”时，工作台展示 Agent 本次实际读取的需求快照和问题。运营可在页面填写补充说明并重新生成；系统更新项目备注并创建新的 Run，旧 Run 的需求快照和结果继续保留。

工作台按当前 `run_id` 刷新状态和候选，人工确认后不会自动切换到项目中更新创建的其他 Run。运营可通过运行时间和状态下拉查看历史 Run；重新生成前会提示创建新记录，已有候选和确认结果不会被覆盖。候选既可逐条补充活动价与履约说明，也可勾选最多 500 条后一次原子批量确认。候选表固定显示商品图片、SKU、商品名称，三级类目、京东价、协议价等其余商品字段可通过“自定义显示列”选择，设置保存在当前浏览器；金额列仅展示时保留两位小数。

类型5 PPT 方案使用独立工作台，流程和接口说明见《18-ppt-solution-workflow.md》；类型4自由推品流程不与类型5共用候选或导出结果。

### 项目业务状态

类型4项目状态按业务动作推进，不允许在列表中越级手工修改：

`已导入 → 匹配中 → 待选品 → 选品完成 → 已生成报价 → 已投标 → 已中标 / 未中标`

- “已导入、匹配中、待选品”由项目创建、Agent 启动和候选生成自动识别。
- 本次 Agent 失败、取消、需要补充信息或没有候选时，项目不会错误停在“匹配中”；存在历史候选时恢复“待选品”，否则恢复“已导入”。Run 本身仍保留真实失败状态和安全错误信息。
- “选品完成”由运营确认右侧人工选择结果触发；“已生成报价”由成功导出触发；“已投标”和最终结果由运营明确确认。
- 选品完成或已经导出时，可以“返回调整选品”。已经生成的历史导出文件不会被覆盖，再次完成并导出会生成更高版本。
- 项目列表、普通详情与自由推品工作台使用一致的状态名称和颜色；选品完成后的详情仍保留左右两栏，以只读方式展示 Agent 推荐与人工最终选择。

映射页会读取当前模板真实的工作表、表头和物理列号。与商品主数据正式列名相同的列会自动匹配，运营可以搜索并调整；重复模板表头可按各自列号确认映射，同一个商品字段也可同时映射到多个模板列。页面方向显示为“模板列 → 商品字段”，新确认映射保存为 V2 `列号 -> 字段 key` 列表；旧版 `字段 key -> 唯一表头` 映射仍可读取和导出，现有 Agent 流程不受影响。

可选数据源包括商品主数据正式 43 列，以及人工确认的“是否厂直”。新生成候选会冻结这些商品字段和供应商名称，导出使用候选创建时快照，避免商品后来修改导致推荐历史漂移。该功能上线前创建的历史候选没有新增快照字段时，对应导出单元格为空。

## 2. DeepSeek 配置

后端通过以下环境变量读取配置，API Key 留给部署人员填写：

```env
DEEPSEEK_API_KEY=
DEEPSEEK_BASE_URL=https://api.deepseek.com
DEEPSEEK_MODEL=deepseek-chat
DEEPSEEK_TIMEOUT_SECONDS=60
DEEPSEEK_MAX_TOKENS=4096
DEEPSEEK_PROMPT_VERSION=free-recommendation-v1
```

API Key 为空不会阻止后端启动，但不能执行 Agent。错误日志和业务错误不得包含密钥、Provider 原始响应或请求中的敏感信息。

## 3. Agent 安全约束

- Type-4 仅以严格 Pydantic JSON Schema 进行一次需求解析；它不选择类目、不检索候选、不生成商品排序、评分或逐条理由。
- 类目原词和语义近义词仅用于后端确定性 SQL 的商品一级、二级、三级类目匹配；AI 不获取数据库工具或商品候选 ID。
- 数据库按已解析的数值、明确品牌和明确类目硬条件查询并保存所有符合条件的商品；候选顺序稳定，页面“评分”取商品主数据 `positive_rating`，不参与筛选。
- Provider 结构化 JSON/Schema 输出失败会附带脱敏校验位置纠错重试一次；第二次仍失败时 Run 安全标记为 `FAILED`。不会持久化或记录原始 DeepSeek response、完整 Prompt 或候选商品 JSON。
- Agent 不接收 SQL 工具，不接触数据库连接信息，不直接写正式业务库。
- 正式商品状态、价格、确认、快照、审计和导出由后端确定性服务重新校验。
- 人工确认的活动价、发货/库存状态、厂直、履约说明和依据会完整返回工作台，并可映射到导出模板。确认更新采用 PATCH 语义：未提交的字段保留原值，显式 `null` 才清空。
- 模板映射至少需要一项字段，不能确认空映射。导出仅覆盖连续模板数据区中的映射业务列，因此不会留下本次确认数量以外的旧示例商品；标题、表头、样式、公式和其他工作表保持不变。
- 导出后的 Run 如再次修改或新增人工确认，会从 `EXPORTED` 回到 `CONFIRMED`，表示必须重新导出最新确认结果。

## 4. 前后端对接边界

A 已冻结的项目创建与模板映射接口直接使用。B 已提供的 Run、详情、候选、逐条确认和批量确认接口均通过前端 `src/api/recommendation.ts` 调用，完整前缀为 `/api/v1/recommendation-projects`。批量确认由服务端在一个事务中重新校验全部候选的商品和供应商状态，任何一项失效都会整批拒绝。

模板映射工作台通过 `GET /api/v1/bid-projects/{project_id}/recommendation-templates/{file_id}/structure` 按所选 Sheet 和表头行读取真实列结构；该接口复用 `recommendation:create` 权限，只读取已保存且摘要校验通过的项目模板。

后端 Job 通过 `RecommendationServiceJobPort` 与 B 的持久化服务对接；AgentRunner 通过 `RecommendationServiceTools` 查询真实类目和商品。C 不依赖 B 的 Repository，也不直接访问数据库。

当前本机 `TASK_MODE=inline` 时，创建 Run 的请求会等待 Agent 完成，前端超时为 5 分钟。正式 ARQ 后台执行仍需基础设施适配；取消接口尚未开放。

确认结果导出由 `20260923_0040` 提供：项目必须处于 `READY` 或 `EXPORTED`，Run 必须处于 `CONFIRMED` 或 `EXPORTED`，且至少存在一条人工确认候选。导出仅写入已确认候选，保留当前已确认推荐模板的格式、公式和字段映射；每次生成独立 `RECOMMENDATION_EXPORT` 附件及导出审计记录。人工确认可填写“是否厂直”三态（待确认／是／否），系统和 AI 不推断该值。导出和下载均要求 `recommendation:export`；下载文件名按 UTF-8 标准编码，支持中文名称。

## 5. Requirement V6：数值、明确品牌与类目分配文本

解析结果按边界保存到 Run JSON；缺少类目、品牌、预算、价格或数量不会自动进入 `NEEDS_INPUT`。

- Hard constraints：`agreement_price_*`、明确说明“京东价”时的 `jd_price_*`、明确数字的 `discount_rate_*`、`gross_margin_*`；以及仅在客户明确强制提出时才写入的 `required_brands`、`explicit_category_keywords`。未指明价格口径时，“200 元以内”写入协议价范围；折扣率 8 折写为 `0.8`。
- 类目语义：Agent 将明确类目原词和同义/近义类目词写入 `category_intents`，数据库在商品一级、二级、三级类目名称中做任一词匹配；未明确指定类目时不使用这些字段。
- 直接商品类目：客户使用“需要、要、采购、推品、需求”等直接提出水杯、保温杯、随行杯、双肩包、锅具等具体商品类型时，Agent 将这些词写入 `explicit_category_keywords`，并将原词与杯具、水具等近义类目词写入 `category_intents`。场景词如“出游、送礼、福利”不因此成为类目。
- 类目分配文本：当文本明确给出“家电 250、厨具 135、日用 115”时，Agent 将家电、厨具、日用写入 `explicit_category_keywords`，并写入语义近义词 `category_intents`。250、135、115 仅是业务背景，不校验库存、不创建订单、不代表下单数量，也不限制候选数量；所有符合硬条件及这些类目的商品都会入池。
- 点位映射：模块4业务口径中，“点位”复用正式商品的 `gross_margin`（毛利率）字段，6% 写为 `gross_margin_min=0.06`。
- 非筛选信息：未强制指定的品牌、场景、用途、节日、人群、特价、物流、一件代发、库存、厂家直发、销量、评分和卖点不参与 SQL 筛选、排序或逐条理由，也不触发补充需求。所有数量、名额和配额数字均不参与；只有类目分配文本中明确出现的类目名称会进入类目筛选。

候选池只按类目、品牌和数值硬条件查询；所有命中商品均持久化为候选，不进行场景相关性排序或 AI 逐条推荐。候选列表以服务端分页返回，页面评分仅展示商品主数据 `positive_rating`。

不再创建或更新人工核验项，`PATCH /manual-checks` 已移除。历史 `manual_flags` 和旧 Run JSON 仍可读取，但不会影响单条确认、批量确认或导出。

## 6. 模板派生字段

模板字段选择器增加派生字段 `supports_jd_or_sf`（“是否支持京东或者顺丰物流”）。它只检查候选冻结快照中的 `shipping_courier` 是否含京东、顺丰或 SF：有明确表达输出“是”，空值、普通或未知物流均输出“待确认”，绝不武断输出“否”。安全自动映射别名包括：名称→`product_name`、大客户协议价→`agreement_price`、毛利→`profit`、毛利率→`gross_margin`、采销→`purchasing_agent`、是否厂直→`factory_direct`。
