# ADR-0028：商品价格原值精度扩展

状态：ACCEPTED
日期：2026-09-18

## Context

正式商品大表的价格列包含超过 4 位小数的业务原值，例如成本价
`109.123595505618`，后续模板也可能出现更长的小数。价格必须保留 Excel 底层原值，不能按显示格式
或数据库旧精度静默四舍五入。原 `DECIMAL(18,4)` 无法满足该要求。

## Decision

- `cost_price`、`market_price`、`jd_price`、`agreement_price`、
  `agreement_purchase_price`、`jd_self_operated_price` 统一使用 MySQL
  `DECIMAL(65,30)`，即最多 35 位整数和 30 位小数。
- 对应 SQLAlchemy Model 与 Pydantic 写入 Schema 同步使用 65 位总精度、30 位小数；导入和手工维护
  均不自动四舍五入价格。
- 商品查询 API 的价格字符串至少保留 4 位小数；第 5 位起只移除无意义的尾随零，所有有效数字完整
  返回。例如 `160` 返回 `160.0000`，`100.1234500` 返回 `100.12345`。
- `profit` 仍使用 `DECIMAL(18,4)`，Excel 公式结果按显示精度消除浮点尾差；比例字段仍按数据库小数
  保存并限制为 4 位小数。
- Excel 数值单元格本身受 Excel 约 15 位有效数字限制；需要超过该限制的精确小数时，来源单元格应以
  文本形式提供，系统按 Decimal 解析后原样保存。

## Consequences

- Revision `20260918_0034` 仅扩大六个价格列，不重算或改写既有价格。
- 六列中已有索引继续保留；单列存储空间增加，但商品主数据规模下可接受。
- API 不返回数据库定长补齐的 30 个小数位，避免前端出现大量无意义尾零，同时不损失有效精度。
- 降级到 `DECIMAL(18,4)` 前会检查既有值；任何值会丢失小数精度或超出旧整数范围时，降级直接中止。
- 30 位小数是 MySQL DECIMAL 的最大 scale。若未来必须保存超过 30 位小数，应重新评审字段语义，
  不能使用 Float 或静默截断。
