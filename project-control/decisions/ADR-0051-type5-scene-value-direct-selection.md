# ADR-0051：类型 5 场景与性价比两阶段直接选品

状态：ACCEPTED
日期：2026-10-09

## 背景

ADR-0050 已使类型 5 按价格档直接产出指定数量商品，但当时 AI 只从受控窗口选择少量核心商品，剩余商品由后端补齐。该机制无法保证最终每一件展示商品都经过场景相关性和性价比判断，也未在页面区分冻结候选池与 AI 最终结果数量。

## 决策

- 类型 5 继续独立维护与类型 4 同口径的需求解析、受控类目和正式商品硬条件召回；类型 4 不修改。
- 后端冻结完整候选池时，将总数量及每个价格档的数量写入既有 Run 配置快照；候选被直接选品裁剪后，统计仍可审计和展示。
- 每个价格档的全部冻结候选按输入预算拆为受控批次。首轮保留压缩后的规格和卖点，并用 `PPT_AI_ASSESSMENT_CONCURRENCY`（默认 4）受控并发评分；AI 仍对每一件商品基于客户原始场景、商品规格/卖点、品牌、协议价、京东价、折扣率、销量和好评率给出场景、价值与综合评分。
- 高分短名单的最终比较保留完整的相关商品字段和首轮评分，避免首轮压缩文本降低最终精确选品质量。服务端为每批和最终比较记录候选数、输入字符数、重试次数、总耗时及 DeepSeek 返回的 Token 用量。
- 后端按 AI 综合评分形成高分短名单；若短名单可安全放入一次输入，AI 再选择恰好 `item_count` 件最终商品。若目标数量本身超出最终比较输入预算，后端仅按已完成的全量 AI 综合评分取前 N 件，绝不以未评估商品补数。
- AI 只能使用服务端短编号，所有输出经 Schema、数量、重复、价格档与冻结候选校验；结构错误自动重试一次。
- 直接选品结果保存 AI 综合评分和固定说明，随后仍由人工在候选表中勾选确认。
- 类型 5 新 Run 创建后立即返回 `QUEUED`，由现有 TaskQueue abstraction 在响应后执行；Web 工作台轮询 Run 状态。Local-First `TASK_MODE=inline` 使用 FastAPI 后台任务，已配置的真实队列可复用同一派发边界。
- 直接选品 Run 冻结完整候选池后必须保持 `RANKING`；只有 AI 裁剪完未入选商品并写入最终数量后，才依次进入 `CANDIDATES_READY`、`WAITING_CONFIRMATION`。因此候选表只能展示最终 AI 匹配结果，冻结池数量仅作统计展示，不能被提前勾选或批量确认。

## 后果

- 大候选池可能产生多次 AI 评分请求，调用成本仍高于原核心种子方案；受控并发和首轮紧凑字段降低墙钟耗时，但受限于提供方并发/限流上限。最终展示商品仍均经历 AI 场景/价值评估。
- 无新表和 Alembic Migration；统计存放在既有 `ppt_config_snapshot` JSON，历史 Run 没有统计时页面显示为空。
- `RecommendationRun` 读取接口新增可选 `ppt_frozen_pool_statistics`，仅类型 5 新 Run 有值；权限不变。
